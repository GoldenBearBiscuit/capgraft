## 1. 背景

### 1.1 一句话问题

我们不是没有测试，是没有**测试的账本**。测试跑在哪里、覆盖了哪条需求、这次改动影响了哪些用例、失败到底是真是假——这四个问题，今天都要靠问人。

### 1.2 五个断点

1. **需求到测试断链。** 需求在需求系统，用例在用例系统，中间靠人脑记。需求改了，没人知道哪些用例已经失效。
2. **测试结果不可信。** 无 flaky 治理，红灯靠"重跑到绿"消化。团队对红灯脱敏之后，真失败也会被一起忽略。
3. **证据不可达。** 失败后要翻 CI 日志、翻群聊、找当时谁在看。一次定位平均消耗 30 分钟以上，且不可复用。
4. **门禁靠人。** 谁能合、要不要补测试、覆盖率跌了要不要拦，全靠 TL 记性和口头约定，没有留痕。
5. **智能体用不了。** CI、用例库、环境配置都是私有接口，coding agent 无法调用，只能在人的中转下工作。

### 1.3 为什么现在做

- **规模效应已经到了。** 一次提交通常只影响不到 0.1% 的用例（Google 公开数据）。没有依赖图做测试选择，全量跑一次的时间会随仓库线性上涨，最终没人等得起，只能降频，等于放弃门禁。
- **智能体已经能写测试，但缺两样东西**：能调用的手（MCP 工具）和能判断的依据（追溯 + 证据）。这两样都是平台该提供的，不是 agent 自己能长出来的。
- **成本是复利的。** 回归集只进不出，flaky 只重跑不根治，两年后维护成本吃掉整个团队的产出。

### 1.4 现状基线（首次评审前补齐）

| 指标 | 当前值 | 说明 |
|---|---|---|
| 服务数 / 仓库数 | 【待填】 | |

## 2. 目标与非目标

### 2.1 目标（12 个月）

| 编号 | 目标 | 可验证标准 |
|---|---|---|
| G1 | 追溯闭环 | 任一需求可在 3 次点击内看到：代码改动、测试结果、缺陷、上线记录 |
| G2 | 门禁自动化 | 合并与发布的关键判断 100% 由配置驱动；人工绕过必须留痕并经指定角色审批 |
| G3 | flaky 可控 | flaky 率 ≤ 2%；检测到隔离 ≤ 24h；修复中位数 ≤ 7 天 |
| G4 | 证据直达 | 任何失败在 PR 页面一站可查：日志、截图、录屏、trace ID、复现命令 |
| G5 | Agent 可调用 | 暴露 ≥ 8 个 MCP 工具，覆盖查询、执行、取证、变更四类动作 |

### 2.2 非目标（明确不做，防止范围膨胀）

- ❌ **不自建测试执行引擎。** 复用现有 CI 与 Playwright / Appium / JUnit。我们只做调度入口和结果归集。
- ❌ **不自建需求管理系统。** 需求仍在现有系统，我们只做 ID 映射与索引。
- ❌ **不做通用 SaaS，不对外售卖。** 只服务本公司内部。
- ❌ **不做性能压测平台。** 只接收压测结果并纳入门禁。
- ❌ **不做 AI 自动修 bug。** V2 之后再评估。
- ❌ **不以「看板访问量」作为成功指标。** 见第 8 节反指标。

| 角色 | 主要诉求 | 关键动作 |
|---|---|---|
| 开发者 | 提交前知道会不会挂，挂了能立刻知道原因 | 看 PR 证据卡片、按影响面跑用例 |

| 合规 / 审计 | 能举证"这条需求确实被测过" | 导出追溯矩阵、查审批留痕 |
| Coding Agent | 能查到事实，而不是被告知 | 调 MCP 工具 |

## 4. 核心概念与数据模型

### 4.1 五个实体

```
Requirement ──< Change ──< TestRun >── TestCase
      │            │           │          │
      └────────────┴───────────┴──────< Defect ──> Incident
```

| 实体 | 关键字段 |
|---|---|
| Requirement | `req_id` `title` `owner` `risk_level` `acceptance_criteria` `source_url` `affected_services[]` `version` |
| Change | `change_id`(PR) `repo` `commit_sha` `author` `req_ids[]` `services[]` `build_id` `merged_at` |
| TestCase | `case_id` `title` `owner` `type`(unit/service/e2e/perf) `automated` `source_path` `req_ids[]` `risk_tags[]` `last_run_at` `status`(active/quarantined/retired) |
| TestRun | `run_id` `case_id` `build_id` `result` `duration` `attempt` `evidence_urls[]` `trace_id` `env` |
| Defect | `defect_id` `severity` `found_stage`(dev/presubmit/postsubmit/release/prod) `related_req[]` `related_runs[]` `escaped` `postmortem_url` |
| FlakyRecord | `case_id` `detected_at` `flip_rate` `window` `state` `assignee` `sla_due` |

### 4.2 三条不可妥协的设计原则

1. **元数据随代码走，数据库只是索引。** 用例的 owner、关联需求、风险标签写在仓库里的 `testcase.yaml` 或测试文件头注释中，平台定期抓取建索引。好处：元数据能随代码一起 review、一起回滚；平台挂了可以重建；不会出现"平台里改了但代码里没有"的双份真相。
2. **URL 是一等交付物。** 每个实体必须有稳定、可粘贴、可点开的链接。做不到可点的证据，等于没有证据。
3. **判断基于证据对象，不是状态字符串。** 不允许出现"已通过"这种没有指向的结论，通过必须能追到某次 run 和它的产物。

## 5. 功能范围

### 5.1 MVP（0–3 个月）：让链路先通

**M1 追溯索引器**

- 用户故事：作为测试工程师，我想知道某条需求对应哪些代码和用例，不用去问人。
- 采集源：Git（PR/commit/OWNERS）、CI（job/run/artifact）、需求系统、用例元数据文件。
- 验收标准：
  - 支持至少 1 套需求系统 + 1 套代码托管 + 1 套 CI 的对接；
  - 全量重建索引 ≤ 30 分钟，增量同步 ≤ 2 分钟；
  - 索引失败不影响 CI 主流程（旁路读取，只读不写）。

**M2 PR 证据卡片**

- 用户故事：作为开发者，我在 PR 页面就能看到这次改动影响了什么、测了没有、挂了长什么样。
- 卡片内容：关联需求、影响服务、受影响用例数、覆盖率增减、失败证据链接（日志/截图/录屏/trace）。
- 验收标准：
  - 提交后 60 秒内自动回帖；
  - 每个失败至少带 1 个可点开的证据链接，链接失效率 < 1%；
  - 卡片结构稳定，不因 CI 系统差异而变。

**M3 门禁规则引擎 v0**

- 规则用 YAML 写，进仓库、走 review、可回滚。
- 验收标准：支持 3 类规则（必须通过的测试集、增量覆盖率阈值、P0 用例不得跳过）；规则变更留审计；绕过需指定角色审批并生成记录。

```yaml
gate: presubmit
rules:
  - id: unit-must-pass
    when: changed_paths matches "src/**"
    require: test_result(unit) == pass
  - id: diff-coverage
    when: true
    require: diff_coverage >= 80%
  - id: p0-no-skip
    when: services intersects ["payment"]
    require: none(test_case.status == skipped where risk == p0)
  - id: has-requirement
    when: pr.labels contains "feature"
    require: pr.req_ids is not empty
on_fail: block
bypass:
  requires_approval: [tech-lead, qa-lead]
  audit: true
```

**M4 孤儿用例报告**

- 定义：无需求链接，或 180 天未执行。
- 验收标准：每周自动生成，按 owner 分组，可直接生成下线工单。

### 5.2 V1（3–6 个月）：让结果可信

**M5 flaky 生命周期**

状态机：`detected → quarantined(24h 内) → assigned(7d 内) → fixed | retired`

- 检测：同 build 同代码多次执行结果不一致，或历史 flip rate 超阈值。
- 退出：14 天未修复自动提议下线，需 owner 确认。
- 验收标准：检测准确率 ≥ 90%（抽样人工校验）；隔离动作不阻塞合并；每次状态变更写审计。

**M6 测试选择（TIA）**

- 基于依赖图（构建目标 / import 关系 / 服务调用关系）算出受影响用例。
- 验收标准：漏选率 ≤ 1%（以全量跑的结果为基准做回溯校验）；平均选中比例显著低于全量，presubmit P90 ≤ 15 分钟。

**M7 追溯矩阵导出**

- 需求 → 设计 → 代码 → 用例 → 结果，导出 Excel/CSV，供审计举证。
- 验收标准：矩阵中每个断言都能点回源实体；导出内容与线上一致（同一快照版本）。

### 5.3 V2（6–12 个月）：让 Agent 接进来

**M8 MCP Server + Skills**

| 工具 | 用途 | 权限 |
|---|---|---|
| `query_traceability(req_id\|pr_id)` | 查一条需求/PR 的完整链路 | 只读 |
| `list_affected_tests(commit \| paths)` | 算受影响用例 | 只读 |
| `run_selected_tests(ids, env)` | 跑指定用例 | 需环境白名单 |
| `get_evidence(run_id)` | 取证据 URL 集合 | 只读 |
| `get_flaky_report(window)` | flaky 排行与状态 | 只读 |
| `query_service_deps(service)` | 服务依赖与调用链 | 只读 |
| `create_defect(run_id, severity)` | 建缺陷并挂证据 | 写入，需幂等 |
| `toggle_feature_flag(name, value, env)` | 灰度开关 | **需人工审批** |

配套 Skill：把"查需求 → 算影响 → 跑用例 → 取证据 → 建缺陷"写成固定步骤，agent 按步骤执行，不即兴发挥。

**M9 变更影响分析**：改一个接口，预估影响哪些服务、哪些用例、哪些历史缺陷。

**M10 发布门禁与灰度联动**：发布单自动带上门禁结论；灰度异常自动触发回滚建议。

## 6. 关键流程

### 6.1 一次提交

1. 开发者 push → PR 自动带上需求 ID（模板强制）
2. 60 秒内 bot 回帖：影响面 + 受影响用例 + 预跑结果
3. 门禁按 YAML 规则判定，不通过则 block，失败带证据链接
4. 通过后进入合并队列，全部通过才合
5. 合并后全量回归 + flaky 检测，异常隔离并派单

### 6.2 一个 flaky 用例的一生

```
检测(24h内) → 隔离(不阻塞合并) → 按 owner 派单(7d) → 修复 → 回归监控 7 天 → 解除隔离
                                              └→ 14d 未修 → 提议下线 → owner 确认 → 删除
```

关键：**owner 由元数据决定，不靠人指派**。没有 owner 的用例本身就是不健康信号。

### 6.3 一次事故回溯

事故单 → 自动关联：涉及需求、最近变更、相关用例及其历史结果、是否曾被隔离。

- 若该需求有用例但未执行 → 归因「门禁失效」
- 若有用例且执行了但没检出 → 归因「用例有效性不足」，进入用例评审
- 若无用例 → 归因「覆盖缺口」，自动生成补测需求

这一步是整个产品的价值闭环：**逃逸缺陷不是终点，是追溯链的校验器。**

## 7. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 索引重建 ≤ 30 min；增量同步 ≤ 2 min；PR 卡片 ≤ 60 s；查询 P95 ≤ 1 s |
| 可用性 | 平台故障不得阻塞 CI 与合并（降级为「无卡片、无附加门禁」，保留 CI 原生门禁） |
| 安全 | 代码与测试产物不出内网；测试数据脱敏；MCP 工具按角色鉴权，写操作全审计 |
| 合规 | 审计日志保留 ≥ 1 年（按行业要求可调）；追溯快照支持按版本导出 |
| 可维护 | 所有对接以 adapter 方式实现，新增一套需求/CI 系统不改核心 |

## 8. 度量

### 8.1 成功指标

| 指标 | 定义 | 当前 | 12 个月目标 |
|---|---|---|---|
| 追溯覆盖率 | 有测试链接的在研需求 / 全部在研需求 | 【待填】 | ≥ 90% |
| 孤儿用例占比 | 无链接或 180 天未执行 | 【待填】 | ≤ 10% |
| flaky 率 | flaky 结果 / 总结果 | 【待填】 | ≤ 2% |
| flaky 修复中位数 | 检测 → 修复 | 【待填】 | ≤ 7 天 |
| presubmit P90 | push → 结果 | 【待填】 | ≤ 15 min |
| 测试选择漏选率 | 未选中但实际会失败的用例占比 | — | ≤ 1% |
| 逃逸缺陷率 | 生产发现 / 全部发现 | 【待填】 | 下降 50% |
| 门禁绕过次数 | 人工 override | 【待填】 | 0，且全部留痕 |
| 变更失败率 | 合入后回滚或热修占比 | 【待填】 | ≤ 5% |

### 8.2 反指标（出现即视为设计失败）

- 看板 PV 高但门禁绕过也多 → 说明平台只是"展示"，没在"管理"
- 用例总数上涨但孤儿占比不降 → 说明在做数量不做质量
- PR 卡片被关掉 / 折叠 → 说明信息密度不对，或没人信它

## 10. 风险与依赖

| 风险 | 影响 | 对策 |
|---|---|---|
| 依赖 CI 改造，被其他团队排期阻塞 | 高 | MVP 只做旁路只读，不改 CI；门禁以"附加检查"形式接入 |
| flaky 治理触动责任归属 | 中 | owner 由元数据决定而非指派；SLA 先宽后紧，前 3 个月只提示不考核 |
| 追溯字段靠人填，必然衰减 | 高 | 能自动推导的一律不让人填；推导不出的用门禁兜底（如"feature 类 PR 必须有 req_id"） |
| 做成"又一个看板" | 高 | 成功指标不含访问量；每个功能必须能改变一个决策 |
| 需求系统有多套 | 中 | MVP 只接一套，其余走 adapter，不做兼容性军备竞赛 |
| 用例管理自研 or 采购未定 | 中 | MVP 先接现有（MeterSphere / TestRail / 自研均可），接口先行 |

## 11. 开放问题（需评审拍板）

1. 用例管理系统自研还是采购？若采购，元数据文件与平台谁是主？
2. 是否要求跨仓追溯（一个需求横跨多个仓库）？MVP 是否值得支持？
3. 审计保留期的硬要求是多少？（金融类通常 6 个月至 5 年不等）
4. Agent 生成的用例如何纳入门禁？建议：**单列标记 human / AI 来源**，AI 用例先只计入"建议覆盖"，不直接计入覆盖率门禁，避免刷分。
5. 门禁绕过允许的审批角色是谁？是否需要两人签？
6. 平台自身的 oncall 归属？

- `kubernetes/test-infra`（Apache-2.0）—— prow 门禁、tide 合并队列、testgrid 看板、triage 失败聚类、kettle 指标入库、gcsweb 证据展示。建议只读 `config/jobs` 与 `OWNERS` 文件。

- `itsallcode/openfasttrace`（GPL-3.0）—— 扫描代码与测试里的 `req~` / `utest~` 标签，生成追溯矩阵，报缺口与孤儿。
- `strictdoc-project/strictdoc`（Apache-2.0）—— 需求即代码，追溯视图 + ReqIF/PDF/Excel 导出。
- `useblocks/sphinx-needs`（MIT）、`doorstop`（LGPL）、`bmw-software-engineering/trlc`（GPL-3.0）。

论文（按子问题）：
