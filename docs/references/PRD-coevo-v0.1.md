# PRD · 协同进化个人 Agent（代号 coevo）

- 版本：v0.1（评审稿）
- 日期：2026-11-15
- 状态：待评审，未进入实现

---

## 0. 一句话

一个跑在个人工作流上的 agent：**从你的真实摩擦里找方向，从外部项目里取能力，但不许新增概念**——每绕一圈，允许改的层级只上移一级。

也就是说：它是「能力增长」与「概念守恒」的联立约束求解，不是又一个技能库。

---

## 1. 背景与问题

### 1.1 现状

现有自进化 agent（Hermes / GenericAgent / OpenSpace / DGM 系）解决的是「技能怎么长出来」：

- 从执行轨迹里结晶技能，加质量分，用向量或名字检索复用
- 评价方式是跑分，改得动就留下

它们共同缺一层：**技能长出来之后，概念怎么不稀释**。技能库胀到几百条，同义技能并存、同一概念多个实现，检索命中率下降，维护成本失控。这个现象所有人都在踩，但还没进任何分类表。

### 1.2 已被实证的失败

清华 THU-Agent（arXiv:2611.03219）把 harness 沿三个任务连续进化：

- SWE-Bench 进化到 94.0%，再去 FeatureBench 进化，第五轮 SWE-Bench 掉到 32.0%（−66%）
- 病因不是「忘了知识」，是**上一轮为适配任务 A 写进 harness 的局部假设，压掉了任务 B 需要的假设**，他们归纳为 verification / workflow / budget 三类冲突

### 1.3 机会

那篇论文的解法方向全是学习方法层面的（记忆机制、任务优先级、渐进学习），**没有一条是结构约束层面的**。而三类冲突的根源是概念没有抽象层——每次进化只能把某个任务的特例硬编码进去。

**我们要做的，就是补这条结构约束，并在别人已经测崩的设置上证明它能把曲线压平。**

## 2. 目标与非目标

### 2.1 目标（v1）

| # | 目标 | 可验证形式 |
|---|---|---|
| G1 | 摩擦可观测 | 连续 7 天记录，产出五类摩擦的结构化日志 |
| G2 | 吸收有方向 | 每轮吸收的动机能回溯到具体摩擦事件 |
| G3 | 概念可守恒 | 引入新类型必须过登记门，未登记即失败 |
| G4 | 边界可判定 | 每个抽象自带可执行反例，反例失败即拒收 |
| G5 | 纵深可控 | 每轮变更记录所属层级（L0–L4），禁止跳级 |
| G6 | 可回滚 | 任意一轮变更可单独撤销 |

### 2.2 非目标（v1 明确不做）

- ❌ 不做通用 agent 框架（不重造 tool calling / 记忆系统）
- ❌ 不做 L1（权重更新）与 L3/L4（改进器/判据）的自动修改
- ❌ 不做自动吸收——agent 只提案，落盘由门禁和人
- ❌ 不做向量检索、embedding、RAG（判定链里不出现相似度）
- ❌ 不做多人协作与云端同步
- ❌ 不做 UI（v1 是 CLI + 文件）

## 3. 核心概念

| 术语 | 定义 | 判定方式 |
|---|---|---|
| **概念** | 一个有唯一载体类型、有明确粒度位置、有不变量的东西 | 是否在 `concepts.yaml` 登记 |
| **投影** | 能把已有概念无损表达成另一个粒度的函数 | 不变量 + 反例可跑通 |
| **摩擦** | 行为里可观测的缺口，五类：重复/搬运/等待/返工/纠正 | 是否命中封闭枚举 |
| **反例** | 只改一个特征就翻转归属的实例 | 必须可执行 |
| **concept_diff** | 一轮变更的结构化产物：consumed / projected / introduced | introduced 必须为空或已批 |
| **纵深** | 本轮改动触及的最深层级 L0–L4 | 落盘时标注 |

**核心不变量（系统宪法，写进代码不是写进提示词）**

1. 类型准入只有人能批——agent 能写 `concept_diff`，不能写 `concepts.yaml`
2. 行为波动不触发吸收，只有结构性摩擦触发
3. 门禁的判据必须在被更新对象的作用域之外（验收证据不能被它自己改写）

## 4. 用户与场景

**唯一用户：你自己。** 单人、本地、单仓库、代码域。

典型一圈（约 1 周）：

> 周三发现同一段日期截断写了第 4 次 → 记为「重复」摩擦 → 周日的复盘轮里 agent 提案「把它抽象成 month_of」并附反例 → 门禁检查：`concept_diff.introduced` 为空、反例可跑、law 通过 → 落一个函数，概念数不变 → 记录本轮纵深为 L2。

## 5. 系统架构

```
                    ┌──────────────────────────────┐
                    │  人（每周）                   │
                    │  定方向 · 批概念 · 冻结版本    │
                    └───────────┬──────────────────┘
                                │ 提案/裁决
   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
   │① 观测   │──▶│② 抽象   │──▶│③ 门禁   │──▶│④ 落地   │
   │friction │   │共性+反例│   │concept  │   │只增函数 │
   │ .log    │   │         │   │ _diff   │   │         │
   └─────────┘   └─────────┘   └─────────┘   └─────────┘
        ▲             ▲             ▲             │
        └─────────────┴────── 留痕 + 回滚 ────────┘
                     下一圈：只上移一级
```

四个阶段是常驻的；纵深（L0–L4）是每圈的可变深度。

## 6. 功能需求

### M1 · 观测（P0）

采集五类摩擦，**禁止记录解决方案**。

| 需求 | 说明 |
|---|---|
| M1.1 | `friction.log` 为 append-only JSONL，一行一条 |
| M1.2 | 摩擦类型为封闭枚举：`repeat / handoff / wait / rework / correction` |
| M1.3 | 每条只允许三段：类型 + 一句话现象 + 频次；不写「应该怎么办」 |
| M1.4 | 采集方式 v1 为**半自动**：agent 提议，人确认后写入（见开放问题 Q1） |
| M1.5 | 每条带 `resolved` 标记，闭环后置真 |

### M2 · 抽象（P0）

| 需求 | 说明 |
|---|---|
| M2.1 | 输入为一组同类型摩擦事件，输出至少 1 条共性提案 |
| M2.2 | **每条共性提案必须附带 1 个反例，否则视为未提出** |
| M2.3 | 反例格式：`看起来像 → 改一个特征 → 归属翻转 → 判据` |
| M2.4 | 反例必须可执行（能在测试里跑），不可执行的反例仅记录不采纳 |
| M2.5 | 提案必须声明它消费了哪些已登记概念（`consumed`） |

### M3 · 门禁（P0，核心）

四级检查，任一失败即阻断。

| 编号 | 检查 | 失败退出码 |
|---|---|---|
| G-1 | **结构**：新增公开类型是否已在 `concepts.yaml` 登记 | 10 |
| G-2 | **行为**：`projected` 的函数是否通过目标概念的 law | 20 |
| G-3 | **语义**：`introduced` 是否为空或已获人批 | 30 |
| G-4 | **边界**：是否附可执行反例且反例当前通过 | 40 |

| 需求 | 说明 |
|---|---|
| M3.1 | 门禁是一个 CLI 命令，退出码即结论（可进 CI / pre-commit） |
| M3.2 | 失败时输出人话解释 + 一条需要人回答的问题（≤1 句） |
| M3.3 | 允许 escape hatch：显式 `--force-with-reason`，但必须写入 diff 且计入指标 |
| M3.4 | 门禁不得读取模型自评，只读 AST + 测试结果 + 登记表 |

### M4 · 落地（P0）

| 需求 | 说明 |
|---|---|
| M4.1 | 产出形态只有两种：纯函数、适配器；**不产出新类型** |
| M4.2 | 新函数的测试优先复用目标概念已有的 law，不新写 |
| M4.3 | 每轮产出必须生成 `concept_diff.json` 并归档 |

### M5 · 纵深（P1）

| 需求 | 说明 |
|---|---|
| M5.1 | 每轮变更标注层级 L0–L4 |
| M5.2 | 晋级判据：当前层门禁连续 N 圈零例外通过（N 默认 3） |
| M5.3 | 禁止跳级；跳级需人批且记录 |
| M5.4 | L3/L4 的变更只能以**文本提案**形式存在，不可落盘 |

### M6 · 留痕与回滚（P0）

| 需求 | 说明 |
|---|---|
| M6.1 | 每轮一个目录：`rounds/<n>/`，含 diff、日志快照、测试结果 |
| M6.2 | `concepts.yaml` 带版本号与冻结时间 |
| M6.3 | 任意一轮可单点回滚（撤销该轮函数与登记） |
| M6.4 | 概念删除需迁移全部调用方，v1 不允许删除，只允许标记 deprecated |

## 7. 数据模型

### 7.1 `concepts.yaml`（唯一类型真源）

```yaml
version: 3
frozen_at: 2026-11-15
concepts:
  - id: time.date
    carrier: LocalDate
    lattice: { parent: null, rank: 3 }
    domain: 1900-01-01..2100-12-31
    equality: 同日即相等
    boundary: 左闭右闭，不含时间
    invariants:
      - id: roundtrip
        expr: decode(encode(d)) == d
      - id: monotone
        expr: a < b  =>  key(a) <= key(b)
    known_impls: [java.time.LocalDate, Temporal.PlainDate, pandas.Timestamp]
    forbidden: 不承载账期语义（见 billing.period）
    deprecated: false
```

### 7.2 `friction.log`（JSONL）

```json
{"ts":"2026-08-12T09:14","type":"repeat","n":4,"sig":"date->month truncation","note":"第4次写同一段","resolved":false}
```

### 7.3 `concept_diff.json`

```json
{
  "round": 3,
  "consumed": ["time.date"],
  "projected": [{"fn":"month_of","from":"time.date","to":"time.month","loss":"none"}],
  "introduced": [],
  "counterexample": {"looks_like":"month_range(2024-05) -> 5/1..5/31","change":"取唯一值 vs 取 31 个值","verdict":"非投影，属区间"},
  "depth": "L2",
  "gate": "pass"
}
```

## 8. 指标

| 指标 | 定义 | 健康值 |
|---|---|---|
| 概念熵 | 新增概念数 / 吸收轮次 | 随轮次趋零 |
| 结构抖动 | 每轮结构改动次数 | 趋零 |
| 换任务回归跌幅 | 切换任务后原任务通过率下降 | < 10%（对照：THU 那篇 66%） |
| 摩擦闭环率 | resolved / 总摩擦 | > 60% |
| 门禁误挡率 | force-with-reason 占比 | < 10% |
| 漏检数 | 人工抽查 20 个 diff 中的漏网 | 0 |

---

## 9. 验收标准（v1 结束条件）

- 连续运行 4 周，完整跑完 ≥ 10 轮
- `introduced` 非空 ≤ 2 次，且全部经人审并有书面理由
- 概念总数增长 ≤ 3
- 门禁漏检 = 0（抽查 20 份 diff）
- 任意一轮可成功回滚，演练 1 次
- 换任务回归跌幅 < 10%

## 10. 里程碑

| 阶段 | 交付 | 关键动作 |
|---|---|---|
| W1 | 只有观测 | 采集器 + `friction.log`；**不吸收，只记 7 天** |
| W2 | 概念登记表 v0 | 把已有类型抄一遍；只上 G-1（结构门） |
| W3 | 行为门 | 加 G-2（law 跑测）+ 反例格式 |
| W4 | 第一圈真实吸收 | 完整走 ①→④，产出第一份 diff |
| M2 | 对照实验 | 接 THU-Agent 的 `continual-harness-evolution`，带门禁重跑，看回归曲线 |

**W1 不许提前进入抽象。** 否则会设计出一个漂亮但无人使用的本体，这是这类系统最常见的死法。

## 11. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 摩擦采集成本高，坚持不下去 | 方向断供 | v1 允许手工；宁可稀疏不可编造 |
| 门禁误挡导致绕过 | 宪法失效 | escape hatch 显式化 + 计入指标，禁止静默绕过 |
| 过度抽象 | 概念爆炸 | 三个同类才允许抽（rule of three）；两个宁可重复 |
| 概念表腐化 | 门禁空转 | 版本冻结 + 每季复审 |
| 只对自己的域名有效 | 不可迁移 | M2 用外部 benchmark 验证 |

## 12. 开放问题

- **Q1**：摩擦采集是手工确认还是自动监控？自动更准但侵入，且会改变行为本身（观测者效应）。
- **Q2**：`introduced` 的审批颗粒度按类型还是按概念？一个类型可能是多个概念的载体。
- **Q3**：是否需要「概念特区」——隔离区允许外来类型自由存在，只禁止跨边界传播？
- **Q4**：law 的维护成本由谁承担？每加一个概念就多一组 property test。

## 附录 A · 与现有工作的关系

| 参照 | 关系 |
|---|---|
| L0–L4 自我进化分级（腾讯混元等，2026-09，549 篇） | 本产品全程停留在 L2（脚手架级），并拒绝 L3/L4 自动化；L2 恰是该综述中可靠性标准最弱的一层，是其明确的空白 |

| 数据库 schema 集成 / ontology alignment | 借用其冲突分类（granularity conflict 等）与 GAV/LAV 映射形式，但把判定从人审换为可执行检查 |
| Garlan et al. 1995《Architectural Mismatch》 | 本产品的原问题陈述：复用部件的隐含假设互相冲突，必须在集成前显式化 |

## 附录 B · 一张纸的设计取舍

| 选择 | 选了什么 | 放弃什么 |
|---|---|---|
| 判定依据 | 行为（law + 反例） | 名字、向量相似度 |
| 增长方式 | 只增函数，类型受控 | 允许技能自由扩张 |
| 演化节奏 | 采样高频、决策低频 | 每轮任务都触发吸收 |
| 人类角色 | 概念架构师 + 方向提供者 | 代码审批员 |
| 系统边界 | 单人单仓库，做到可信 | 通用框架，做大而全 |
